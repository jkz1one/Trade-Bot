# Reviewed local options recovery

P4 operator surface, 2026-10-12. A separately enrolled operator capability can
submit signed HALT, RESUME, REVOKE_KEY or RESET_LOSS_LOCK requests to the active local PAPER runner.
The existing owner alone applies them. The observer remains read-only and has no
command route, signing key or automatic recovery action. This is local fixture
control, with no broker transport, risk-policy changes or LIVE activation.

## New population and separate credentials

Before initializing a **new** runtime population, set
`runtime.operator_key_file` to an explicit absolute private key-file path. The
[operator-enabled fixture example](../examples/options-local-runtime-operator.json)
extends the existing model-off runtime example with that optional path. Omission
preserves old policy serialization and enables no command transport. Existing
frozen populations cannot adopt a new operator path by editing settings.

Generate an independent 32-byte random secret locally, encode it as 64 lowercase
hex characters, and save it in an owned regular `0600` file inside an owned `0700`
directory. Never use an API key, OAuth credential or observer password. Model and
operator paths/secrets must be separate; the initializer rejects a reused model
secret before creating the population. No key is generated by or saved in the bot.

Initialization records only the operator key hash, a random journal identity and
credential generation. It creates private `operator-inbox` and `operator-receipts`
directories beside the execution journal. The original runtime owner lease and
restore fence cover all journal mutations, including command receipts and audits.

## Review, submit, inspect

Run these commands as the population's filesystem owner, with the installed wheel.
Choose a new review filename each time; review artifacts are create-only.

```sh
python -I -m app.options.operator_cli review \
  --journal /absolute/private/population/options.db \
  --population-id options-runtime-fixture-v1 \
  --key-file /absolute/private/options-operator.key \
  --output /absolute/private/review-1.json

python -I -m app.options.operator_cli submit \
  --journal /absolute/private/population/options.db \
  --review-file /absolute/private/review-1.json \
  --key-file /absolute/private/options-operator.key \
  --action RESUME --actor local-operator \
  --reason 'Reviewed current account, protection, costs and runtime evidence'
```

Review authenticates the enrolled capability and verifies restore authority in a
read-only committed snapshot. It reports the exact revision, account/position,
supervision, runtime, cost uncertainty, stored loss-control state and entry halt evidence. It performs no feed,
venue, model or order operation. The review artifact grants no authority itself.
Actor is an audited label for the shared signing capability, not proof of an
individually authenticated person or of subjective review quality.

Submit signs the **saved** revision and never refreshes it silently. The command
binds protocol version, journal/population identity, credential generation, a fresh
32-hex command ID, action, actor, reason and issuance/expiry times. HMAC-SHA256 uses
sorted compact UTF-8 JSON of the validated options command. The options protocol
is distinct from equity commands. Default lifetime is 60 seconds; `--ttl` must be
1–300 seconds. Extra authority fields and unsupported actions are rejected.

CLI exit 0 means review saved or request **QUEUED**, not applied. Submit returns a
private receipt-file path. The active runner processes at most one request before
each protection tick. Inspect that JSON for APPLIED/REJECTED; the execution journal
and stored observer retain the authoritative original receipt and actor/reason.
If the runner is stopped, a queued request has no effect and may expire before
consumption. There is no HTTP listener or observer POST route in this slice.

## Recovery gates and durable outcomes

For an explicitly enrolled [native loss-control population](OPTIONS_NATIVE_LOSS_CONTROL.md),
use the same review/submit workflow with `--action RESET_LOSS_LOCK` and an explicit
review reason. This separately signed action requires the exact reviewed revision,
an existing threshold lock, expired cooldown, revalidated complete outcomes,
fresh flat account/supervision, no working order or active runtime task, known costs,
and remaining daily/total loss budgets. It clears only the loss lock/streak, retaining
consumed history, all costs, global limits and any global halt. RESUME cannot replace
this action; RESET_LOSS_LOCK cannot replace RESUME.
For a newly enrolled Degen/Swing family policy, add `--loss-family DEGEN` or
`--loss-family SWING` to reset only that family after its cooldown. The target is
signed and retained in the receipt. Account-wide limits/lock, other family locks,
all economic history and any global halt remain intact. Omitting the target
resets only the account-wide lock and leaves family locks intact. Scope family
reset remains open.

RESUME checks the exact reviewed event revision and uses the same engine recovery
gate inside one authenticated fenced transaction. It requires fresh RUNNING
runtime, fresh matching account/supervision, known model costs, no working orders,
and no stop request. Any unsettled model-call row blocks recovery even if costs
were configured off. A pending decision/model task also blocks signed recovery.
Held-position protection, original limits and normal admission remain in force.
No quote, cost, fill, settlement or flat state is manufactured.

Protection and decisions can advance the journal between review and consumption.
An old RESUME becomes REJECTED with `OPTION_REVIEW_REVISION_CHANGED`; take a fresh
review and explicitly submit a new command. There is no retry that substitutes a
new revision. HALT and REVOKE_KEY reduce authority and remain available with a
stale revision, but still require valid identity, signature, generation and time.
Revocation halts entry and permanently retires that capability in this slice;
key rotation/reprovisioning is not implemented. It does not stop protective work.

Authenticated same-ID/same-body repeats return the original receipt without
re-execution, including after original expiry. A different body under that ID is
rejected. The database records the result before receipt-file publication. A
delivery failure keeps the request for replay and halts entry; replay cannot
clear that later halt. Conflicting receipt evidence also halts entry. If revocation
retires the key before file delivery, the original journal/observer receipt remains
available; the retired key cannot authorize a replay or another action.

Inbox/receipts are owner-only `0700` directories; files are private regular `0600`
JSON, bounded to 16 KiB. Complete files publish through fsynced create-only hard
links; readers never consume a partial publication. Polling caps the inbox at 64
entries. Malformed, oversized, symlink/FIFO, unsigned or mismatched requests cannot
execute. Key loss, revocation, directory/receipt failure or backlog overflow fences
entry while independent supervision continues. Same-user/root hostile filesystem
access remains outside this local capability boundary; target-host isolation and
independent recovery acceptance remain open.

The stored observer shows capability status and bounded original receipts without
reading a signing key or granting recovery authority. Native CLI/read/queue tests
and journal immutability proof do not establish browser visual or host acceptance.
Authenticated provider/model collection, installed release identity, target-host
alerts/off-host recovery, full dashboard and prospective economics remain open.
LIVE remains disabled; main and the frozen deployed experiment are unchanged.
